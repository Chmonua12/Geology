# Монолит Адыгеи

«Монолит Адыгеи» — интерактивное мини-обучение по геологической безопасности. Пользователь проходит четыре учебных этапа, учится распознавать признаки карста, оползней и обвалов, знакомится с инженерной защитой и получает сертификат.

# Игровой ролевой практикум
## Проект «Монолит Адыгеи»

**Тема:** проектирование и совершенствование интерфейса интерактивной образовательной платформы по геологической безопасности Республики Адыгея.

**Цель практикума:** применить UX-методологии, исследовательские методы, тестирование и принципы проектирования интерфейсов к действующему веб-приложению, улучшить пользовательский путь и оценить результат изменений.

# Часть 1. Сеттинг и задача

## 1. Выбор вида деятельности

Наша команда выбрала направление **образование**, а именно интерактивное обучение геологической безопасности.

Разрабатываемое приложение «Монолит Адыгеи» представляет собой образовательную веб-платформу, на которой пользователи изучают опасные геологические процессы через виртуальную экспедицию.

В проекте представлены четыре учебные темы:

1. Карстовые процессы на территории Лаго-Наки.
2. Оползневые процессы в районе Каменномостского.
3. Обвалы и осыпи в горных районах Адыгеи.
4. Инженерные способы защиты склонов и сооружений.

Обучение проходит в интерактивной форме: пользователь изучает изображения местности, находит признаки геологических опасностей, выполняет задания, получает объяснения и проходит мини-игру.

После завершения обучения формируется сертификат и доступен персональный разбор результатов.

## 2. Целевая аудитория

Основная аудитория — школьники 13–16 лет, изучающие географию, экологию и основы безопасности жизнедеятельности.

Дополнительная аудитория — преподаватели, использующие приложение для закрепления теоретического материала, а также пользователи, интересующиеся геологией.

Платформа может использоваться как в классе, так и самостоятельно дома с компьютера или мобильного устройства.

## 3. Проблема проекта

Основная проблема заключается в том, что теоретические сведения о геологических опасностях сложно применять к реальным ситуациям без визуальных примеров и практических заданий.

Дополнительные UX-проблемы исходного интерфейса заключались в недостаточно понятном начале обучения, сложности возврата к незавершённой экспедиции и недостатке итоговой обратной связи.

Пользователь должен понимать, что ему предстоит изучить, сколько времени займёт обучение, на каком этапе он находится и какие темы требуют повторения.

## 4. Предлагаемое решение

Мы разработали интерактивный учебный маршрут с визуальными заданиями, объяснениями ошибок, сохранением прогресса и итоговой оценкой.

Для повышения персонализации в проект были интегрированы:

- GeoChat — ИИ-помощник по геологической безопасности;
- GeoRadar — дополнительные задания для закрепления знаний;
- MCP-сервер — механизм взаимодействия ИИ-ассистента с данными приложения;
- персональная экспедиция — подбор следующего игрового маршрута по результатам прохождения;
- система сбора пользовательских метрик и отзывов.

Главная задача — сделать процесс обучения понятным, последовательным, интерактивным и адаптивным.

# Часть 2. Обобщённый каркас фаз

При проектировании интерфейса мы используем последовательный UX-цикл:

**Понять → Сфокусировать → Создать варианты → Собрать минимум → Проверить → Пересобрать.**

| Фаза | Действия в нашем проекте | Результат |
|---|---|---|
| Понять | Изучение аудитории, анализ существующего интерфейса, ролевые интервью | Выявленные потребности и трудности пользователей |
| Сфокусировать | Выделение проблем начала, продолжения и завершения маршрута | Сформулированная UX-задача |
| Создать варианты | Сравнение способов навигации, подсказок и отображения результатов | Выбор оптимальных решений |
| Собрать минимум | Разработка вводного экрана, сохранения прогресса и блока результатов | Работающий интерфейс |
| Проверить | Юзабилити-тестирование, эвристическая оценка, анализ метрик | Список проблем и результатов проверки |
| Пересобрать | Изменение интерфейса по результатам тестирования | Улучшенная версия приложения |

Во время исследования мы применяем дивергентное мышление — рассматриваем разные потребности пользователей и возможные решения. После этого используем конвергентное мышление, чтобы выбрать наиболее полезные и осуществимые изменения.

Цикл повторяется после каждой проверки пользовательского опыта.

# Часть 4. Правила и ход практикума

Работа выполняется в четыре раунда:

1. Выбор методологии проектирования.
2. UX-исследование пользователей.
3. Оценка интерфейса и тестирование.
4. Разработка прототипа и дизайн-системы.

В каждом раунде результаты предыдущих этапов используются для принятия следующих решений.

Итогом становится улучшенный интерфейс образовательного приложения и обоснование внесённых изменений.

## Раунд 1. Методологии процесса

### Задача

Выбрать методологию разработки и определить, как улучшить взаимодействие пользователя с образовательной платформой.

### Исходная ситуация

Приложение уже содержит интерактивные задания и визуальные сцены. Однако первоначальный пользовательский путь недостаточно объясняет цель обучения, а после завершения маршрута отсутствует полноценная оценка приобретённых знаний.

У команды ограничены время и ресурсы, поэтому необходимо улучшить существующее приложение без полной переработки игровой механики.

### Рассмотренные методологии

**Дизайн-мышление.** Позволяет изучить потребности школьников, определить проблемы, предложить решения и проверить их с помощью прототипов.

**Двойной алмаз.** Помогает сначала исследовать разные пользовательские проблемы, затем выбрать главную, разработать варианты и остановиться на подходящем решении.

**User-Centered Design (UCD).** Предполагает проектирование с учётом возраста, знаний, устройств и условий использования целевой аудитории.

**Lean UX.** Позволяет формулировать гипотезы, быстро изменять интерфейс и проверять результат по измеримым показателям.

**Design Sprint.** Помогает распределить исследование, проектирование, реализацию и тестирование на короткий рабочий период.

### Выбор методологии

Основной методологией мы выбрали **Lean UX**, поскольку проект уже существует, а наша задача — улучшить конкретные пользовательские сценарии за ограниченное время.

Design Sprint применяется для организации работы команды, а UCD — для учёта потребностей целевой аудитории.

### Основная гипотеза

Если добавить понятный вводный экран, отображение прогресса, возможность продолжения и подробные итоги прохождения, то пользователи смогут быстрее ориентироваться в приложении и успешнее завершать обучение.

Для проверки гипотезы используются показатели успешности заданий, времени прохождения, числа ошибок, подсказок и оценки понятности.

### Результат первого раунда

Были определены ключевые направления улучшения: первое знакомство с приложением, навигация, сохранение прогресса, объяснение ошибок и понятный итог обучения.

## Раунд 2. UX-исследования

### Задача

Изучить потребности пользователей, выявить сложности при прохождении виртуальной экспедиции и определить наиболее важные изменения интерфейса.

### Интервью

Для учебного практикума используется ролевое интервью с участником, представляющим школьника 14 лет.

Вопросы связаны с пониманием назначения сайта, сложностью заданий, использованием подсказок и ожиданиями от завершения обучения.

В ходе ролевого сценария были выделены следующие потребности:

- Пользователь хочет понимать задачу до начала обучения.
- Ему важно видеть количество оставшихся этапов.
- После неправильного выбора необходимо получать объяснение.
- Прогресс должен сохраняться после закрытия страницы.
- В конце нужно видеть результат и возможность повторить сложные темы.

Эти наблюдения использовались как исходные предположения для проектирования. Они не заменяют результаты исследования реальных школьников.

### Наблюдение

При анализе пользовательского пути были выделены проблемные ситуации: неопределённость перед началом маршрута, поиск нужных элементов на насыщенных визуальных сценах, прерывание прохождения и недостаточно информативное завершение.

При этом механика интерактивного поиска признаков геологических процессов показала себя перспективной, поэтому её было решено сохранить.

### Персоны пользователей

**Персона 1 — Аня, 14 лет.**

Учится в школе, пользуется телефоном и ноутбуком. Предпочитает короткие интерактивные задания и визуальные объяснения. Хочет понимать, сколько времени занимает обучение и почему выбранный ответ правильный или неправильный.

**Персона 2 — преподаватель географии.**

Использует цифровые образовательные материалы на уроках. Заинтересован в коротких заданиях, понятной структуре и возможности оценить результат обучения.

### Информационная архитектура

Функции приложения сгруппированы по основным задачам пользователя:

| Раздел | Содержание |
|---|---|
| Начало | Регистрация, объяснение цели, запуск или продолжение |
| Обучение | Геологические локации и интерактивные задания |
| Помощь | Подсказки, GeoChat, дополнительные задания GeoRadar |
| Результаты | Сертификат, статистика, итоговый разбор |
| Повторное обучение | Персональная экспедиция и повтор маршрута |

### Карта пути пользователя

| Этап | Действие | Возможная проблема | Решение |
|---|---|---|---|
| Первое посещение | Пользователь открывает сайт | Непонятно назначение приложения | Вводный экран |
| Начало | Запускает экспедицию | Неясен объём заданий | Отображение этапов |
| Обучение | Выполняет интерактивные задания | Сложные термины и ошибки | Объяснения и GeoChat |
| Прерывание | Закрывает страницу | Риск потери прогресса | localStorage |
| Завершение | Получает сертификат | Неясно качество результата | Итоговая статистика |
| Повтор | Хочет закрепить знания | Не знает, что повторять | Персональная экспедиция |

### Результат второго раунда

Был сформирован последовательный пользовательский сценарий: регистрация → знакомство с экспедицией → выполнение заданий → получение обратной связи → просмотр результатов → персональное повторение.

## Раунд 3. Оценка и тестирование

### Задача

Проверить, насколько пользователь понимает интерфейс, может ли выполнить учебный маршрут без дополнительных объяснений и видит ли результаты своих действий.

### Эвристическая оценка

Интерфейс анализируется по принципам удобства использования, включая видимость состояния системы, последовательность действий, предотвращение ошибок и доступность помощи.

Основные проблемы и решения:

| Проблема | Важность | Решение |
|---|---|---|
| Неочевидное начало обучения | Высокая | Вводный экран |
| Потеря активного этапа после прерывания | Высокая | Сохранение прогресса |
| Недостаточно понятные результаты | Средняя | Блок итоговых метрик |
| Сложность отдельных заданий | Средняя | Дополнительные объяснения и GeoRadar |
| Отсутствие персонального повторения | Средняя | Конструктор экспедиции |

### Юзабилити-тест

Для проверки интерфейса определены шесть основных задач:

1. Объяснить назначение приложения.
2. Начать экспедицию и найти признаки карстовой опасности.
3. Продолжить прохождение после перезагрузки.
4. Выполнить задание на выбор наблюдения и защиты.
5. Найти итоговый результат и оценить обучение.
6. Начать повторное прохождение.

В процессе проверки фиксируются успешность действий, время, ошибки, подсказки и первый клик.

### RITE — быстрые итерации улучшения

**Первая итерация** направлена на улучшение первого контакта пользователя с сайтом.

Добавляются вводная информация, цель, продолжительность маршрута, сохранение прогресса и возможность продолжить обучение.

**Вторая итерация** направлена на улучшение завершения обучения.

Добавляются статистика, оценка понятности, комментарий, повторное прохождение и персональный разбор.

### Сравнение результатов

В документации проекта приведён учебный ролевой прогон, демонстрирующий методику оценки.

| Показатель | Исходный интерфейс | После двух итераций |
|---|---:|---:|
| Успешные задания | 4 из 6 | 6 из 6 |
| Время прохождения | 11 мин 40 с | 8 мин 50 с |
| Ошибки | 7 | 3 |
| Подсказки | 3 | 1 |
| Оценка понятности | 3/5 | 5/5 |

**Важно:** это демонстрационные результаты ролевого тестирования, а не подтверждённая статистика реальной аудитории.

### A/B-сравнение

Для учебного сравнения рассматриваются два варианта начала экспедиции.

Вариант A сразу открывает первое задание, а вариант B предварительно показывает цель, длительность и ожидаемый результат.

Основная метрика — возможность начать выполнение без объяснения со стороны преподавателя.

Для рабочего интерфейса выбран вариант B, поскольку он обеспечивает понятный вход в обучение.

### Результат третьего раунда

Были определены критерии оценки интерфейса и внесены изменения в начало, продолжение и завершение маршрута. Для подтверждения улучшений на реальной аудитории необходимо провести отдельные пользовательские тесты.

## Раунд 4. Прототип и дизайн

### Задача

Создать согласованный интерфейс образовательной платформы с повторно используемыми элементами и понятной визуальной системой.

### Структура прототипа

Основной пользовательский путь включает:

**Авторизация → Вводный экран → Четыре учебных этапа → Сертификат → Итоговый разбор → Персональный маршрут.**

Каждый этап содержит собственные интерактивные задания, пояснения и механизмы обратной связи.

### Визуальное оформление

Дизайн приложения основан на природной тематике Республики Адыгея.

Используются изображения горных ландшафтов, зелёные цветовые оттенки, контрастные кнопки и визуальные элементы экспедиции.

Основная задача визуальной системы — сохранить атмосферу геологического исследования, не усложняя взаимодействие с заданиями.

### Компонентный подход

| Уровень | Элементы проекта |
|---|---|
| Атомы | Кнопки, поля, иконки, подписи, счётчики |
| Молекулы | Карточки заданий, варианты ответов, индикаторы прогресса |
| Организмы | GeoChat, GeoRadar, игровые сцены, итоговая форма |
| Шаблоны интерфейса | Экран локации, экран мини-игры, экран результатов |
| Страницы | Основной образовательный сайт и конструктор персональной экспедиции |

### Технологическая реализация

Основной сайт разработан на Python с использованием Django, HTML, CSS и JavaScript.

Для отдельного React-интерфейса персональной экспедиции используется Vite. Bun обеспечивает работу дополнительного REST API, WebSocket и MCP-сервера.

Данные прохождения сохраняются в браузере через localStorage и синхронизируются с серверной базой SQLite. Отдельная SQLite используется Django для учётных записей и сессий.

Через Polza AI реализованы GeoChat и нейросетевой анализ итоговых результатов.

MCP предоставляет ИИ-ассистенту инструменты для чтения учебной статистики и заполнения форм. Изменения передаются в открытый браузер через WebSocket.

Оценки и комментарии пользователей направляются в Google Sheets через Google Apps Script.

# Часть 5. События и оценка

## 1. Игровые события модератора

В ходе практикума преподаватель может вводить дополнительные условия, моделирующие реальные ограничения разработки.

| Событие | Как проявляется в проекте | Предлагаемое решение |
|---|---|---|
| Недоступность ресурса | Polza AI временно не отвечает | Основной учебный маршрут работает без GeoChat |
| Претензия пользователя | Школьнику непонятно, почему его ответ неверный | Добавить пояснение и дополнительное задание GeoRadar |
| Перегрузка интерфейса | Слишком много информации на одном экране | Сохранить фокус на текущей задаче |
| Долгое прохождение | Пользователь не успевает завершить занятие | Продолжение с сохранённого этапа |
| Масштабирование | Необходимо добавлять новые темы и задания | Переиспользовать компоненты и структуру маршрутов |
| Смена аудитории | Приложение используется младшими школьниками | Упростить задания и увеличить количество подсказок |

Каждое событие рассматривается как повод проверить текущую систему и предложить изменение с измеримым результатом.
